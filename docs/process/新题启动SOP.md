# 电赛信号题新题启动 SOP

> 高频采样提示：如果 STM32 ADC 的有效采样率、同步性或输入带宽不够，方案阶段必须检索
> `K-FPGA-001`，把“FPGA + 并行 ADC 冻结窗口”列为候选；同时写清 Nyquist、窗口时长、
> 每周期点数和 FPGA—主控吞吐，不能把 25 MSPS 采样误写成 25 MSPS 连续上传。

> 目的：让 AI 在拿到新题后，能够先建立可验证的方案架构，再选择已有 Knowledge 和 Library 资产，最后生成可落地的 STM32 代码计划。
>
> 本流程不保证题目自动完成。任何 L2 软件模块、来源项目经验或历史参数，都必须按新题的板卡、频率、负载和验收条件重新验证。

## 0. 启动前事实检查

开始设计前必须确认并记录：

| 项目 | 必填内容 |
|---|---|
| 题目与版本 | 年份、题号、基础/发挥要求、勘误 |
| 时间与资源 | 剩余时间、队员、已有板卡、仪器、器件库存 |
| 主控 | MCU、主频、RAM/Flash、FPU、可用定时器/DMA/SPI/ADC/DAC |
| 工程状态 | 工程路径、Git 分支/HEAD/dirty、CubeMX `.ioc`、构建方式 |
| 外部限制 | 禁止使用的仪器、人工换线限制、按键后一键完成要求 |
| 验证基准 | 示波器/信号源/万用表设置、端接、探头倍率、校准状态 |

缺少信息时可以建立带 `待确认` 标记的方案，但不得把假设写成已验证事实。

进入新题前运行 Framework 只读审计：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests/framework_audit.ps1
```

审计失败时先判断是索引/链接漂移还是资产真实缺失；不得忽略失败后继续把资产当作已知可用。

## 1. `01-新题方案与工程基线`

用户只需发送题目原文或清晰图片。AI 必须自行读取：

- `AGENTS.md`、`AI_CONTEXT.md`、`AI_RULES.md`、`AI_INDEX.md`；
- `knowledge/器件知识库/器件清单.md`；
- 本 SOP、比赛现场手册和当前资产索引。

不要求用户重新发送器件清单或复述流程。

### 1.0 ChatGPT 第一阶段草案边界

比赛现场可以先让 ChatGPT 做第一阶段方案草案，但它只负责器件级判断：用哪些器件、总体思路、连接图、各模块职责、关键性能是否大致够用，以及 FPGA 是否值得使用。固定提示词见 [`../templates/chatgpt_phase1_prompt.md`](../templates/chatgpt_phase1_prompt.md)。

给 ChatGPT 的资料默认只包括题目、器件清单、关键原理图/接口表、现场仪器条件和已知限制。完整 Knowledge、Library、`.ioc`、FPGA 源码、历史项目和历史调试日志不默认上传；只有 Codex 读题后认为某条资料对方案选择必要，才摘取相关内容给 ChatGPT。

ChatGPT 输出只能作为“待审查方案草案”。正式进入工程前，Codex 必须重新审查题目、器件能力、采样/幅度/带宽边界、引脚冲突、CubeMX、通信协议和所选 Knowledge/Library，不得直接按 ChatGPT 草案写代码。

FPGA 不是默认使用项。只有当 STM32 或现有 ADC/DAC/模拟器件在采样率、同步性、时序稳定性或处理压力上明显不够，并且 FPGA 能带来明确收益时，才把 FPGA 列为主方案；否则 FPGA 保持为备选或不使用。

### 1.1 建立题目与资源快照

先记录题目、基础/发挥要求、禁止条件、现场器件和仪器。首次输出保持简短，不在
这一阶段展开完整预算、CubeMX 或代码。

### 1.2 快速检索直接相关资产

只检索与题目直接相关的器件、Knowledge 和 Library；不扫描全部 `projects/`，
不因文件存在就认定器件或模块适用。

若题目命中高速原始波形、STM32 ADC 带宽不足或多通道同步采样，先把 FPGA 作为候选器件评估，而不是默认采用。只有判断 FPGA 比 STM32 直采、现有 ADC/DAC 或模拟方案更合适时，才按以下顺序读取：

1. `knowledge/INDEX.md` 中的 `K-FPGA-001` 及其正文；
2. `library/experimental/drivers/fpga_packet/README.md` 和对应 L2 验证记录；
3. 只有选定 FPGA 路线、需要核对位流、接线或 STM32 Adapter 时，才读取
   `projects/已完成项目/FPGA_STM32高速采样桥/README.md`、`VERIFICATION.md`
   和相关源码。

### 1.3 只提交三种候选方案

AI 必须先给用户三种候选：

| 方案 | 默认定位 |
|---|---|
| A | 优先使用现有器件；允许用现有芯片、阻容和通用器件自行焊接电路，优先基础闭环和现场可实现性 |
| B | 加入当前没有、需要额外采购的必须器件，或能显著改善性能的关键芯片/成品模块 |
| C | 低风险保底或不同技术架构 |

每种方案只比较覆盖范围、信号链、器件增量、优点、缺点、最大风险、预计调试量和
回退能力。完成后停在 `SOLUTION_USER_GATE`。用户选择、组合或否决方案之前，不得
进入完整方案、CubeMX、建工程和正式编码。

“现有器件”不等于“现成模块”：只要器件清单中的元件足以实现，现场可焊电路
就可以列入方案 A。对所有自焊电路必须额外写明关键 BOM、预计焊接时间、调试
时间、关键测点、带宽/幅度/稳定性风险以及失败后的旁路或替代方案；未实测前只能
标为待焊接/待验证，不得写成已有模块或 L3 证据。若自焊方案需要比赛现场难以
保证的高速 PCB、阻抗控制或长时间标定，应按风险放入方案 B 或 C，而不是仅因
元件“理论上存在”就放入 A。

### 1.4 用户选择后：把题目改写成验收矩阵

逐条拆解题目，不先写代码：

| 要求 ID | 输入 | 输出 | 范围/精度 | 时间限制 | 是否需自动完成 | 验证方法 |
|---|---|---|---|---|---|---|
| B1/F1… | 频率、幅度、阻抗 | 波形、参数、显示 | 题目原文 | 题目原文 | 是/否 | 仪器或内部测量 |

必须区分：

- 题目明确要求；
- 合理工程假设；
- 当前器件能力；
- 尚未验证的方案推断。

## 5. 画完整信号链和控制链

至少画出：

```text
[信号生成] → [幅度调理] → [输出缓冲] → [被测对象] → [模拟调理] → [测量]
      ↑              ↑             ↑              ↑              ↑
   频率精度       动态范围      负载/端接       带宽/噪声      采样/Nyquist
```

同时画控制链：

```text
[题目状态机] → [服务层] → [驱动/协议层] → [板级 HAL 适配] → [器件]
```

题目状态机、固定标定值和 UI 流程留在项目层；通用算法、协议内核和显式上下文模块才可进入 Library。

## 6. 强制完成五类预算

### 6.1 采样预算

记录：

```text
总吞吐率
÷ 通道数
÷ 每次转换/通信开销
÷ 主循环或服务开销
= 每通道有效采样率
```

然后计算 `Nyquist = 有效采样率 / 2`。需要幅相、FFT 或波形重建时，还要给出每周期采样点数和频率分辨率。超过 Nyquist 的交流信号不得直接用 ADC 波形测量。

### 6.2 幅度与动态范围预算

从信号源到 ADC/DAC 逐级记录：

- 输入、输出和供电范围；
- 增益、衰减和偏置；
- 峰值、RMS、Vpp 的换算条件；
- 运放输出摆幅、ADC 满量程和保护裕量；
- 50 Ω端接、探头和负载造成的幅度变化。

### 6.3 带宽与建立时间预算

检查器件 GBW、SR、滤波器带宽、RMS 芯片响应时间、开关切换时间、DMA/缓存更新时间和闭环收敛时间。

### 6.4 资源与实时性预算

估算：

- 波形表、FFT、采样缓冲和工作区 RAM；
- Flash；
- 单次计算最坏耗时；
- ISR 最长执行时间；
- DMA、定时器、SPI 和引脚冲突。

### 6.5 误差预算

分别记录量化、时钟、增益、偏置、频响、插值、噪声、温漂、负载和标定残差。没有误差预算时，不得承诺题目精度。

## 7. 深入核对选定方案的既有资产

这是正式写代码前的强制二次检索，不等同于 1.2 的快速候选检索。至少读取：

1. 相关 Knowledge 正文、来源、适用/不适用条件和失败案例；
2. 相关 Library README、公开头文件、依赖、测试和验证记录；
3. 当前器件清单及影响选型的器件资料；
4. 本题实际 `.ioc` 和板级句柄事实。

完成复用表并确认适配项、复验计划后，才允许进入正式代码阶段。

### 7.1 方案确认后的硬件交付物

用户选定方案并完成完整架构后，AI必须生成两个配套交付物：

1. `docs/hardware/hardware_connection_overview.svg`，并导出同内容PNG；
2. `docs/hardware/stm32_pin_overview.md`。

硬件连接图采用类似“总体信号链 + 关键程控连接/必要局部电路”的分区形式，至少
标出信号方向、模块名称、STM32功能、关键频率/幅度范围和待确认项。技术连接图
优先用可编辑SVG生成，PNG用于现场查看；不得用装饰性图片代替可核对的工程连接。

引脚总览按模块分组，只列需要STM32程控或与STM32信号引脚相连的连接，例如：

```markdown
### ADS8688

| 模块端信号 | 方向 | STM32引脚 | 外设/功能 | 状态/备注 |
|---|---|---|---|---|
| RST | STM32 → 模块 | PD0 | GPIO_Output | 2025G软件SPI基线 |
| DAISY_IN | STM32 → 模块 | PD1 | GPIO_Output，固定低 | 2025G软件SPI基线 |
| CS | STM32 → 模块 | PD2 | GPIO_Output，低有效 | 2025G软件SPI基线 |
| SCLK | STM32 → 模块 | PD3 | GPIO_Output，软件SPI | 2025G软件SPI基线 |
| SDI | STM32 → 模块 | PD4 | GPIO_Output，软件SPI | 2025G软件SPI基线 |
| SDO | 模块 → STM32 | PD5 | GPIO_Input，软件SPI | 2025G软件SPI基线 |
```

ADS8688在当前板卡上不得默认改为PC10/PC11/PC12硬件SPI。只有用户以后明确要求
重新评估，并完成新接线、CubeMX、驱动和实测闭环时，才能提出迁移方案。

不逐项列仅需供电的VCC、±电源和GND，也不在引脚表中列纯模拟模块之间的连接；
但文档顶部必须保留“所有模块按要求供电并与STM32共地”的安全提示。模块模拟量
直接连接STM32 ADC/DAC、比较器输入捕获、PWM、UART、SPI、I2C、CS、RESET、
ENABLE、IRQ等信号必须列出。

交付分两版：

- **方案建议版**：在用户操作CubeMX前生成，引脚标记为“建议/待确认”；
- **实装确认版**：用户回传`.ioc`和生成代码后，根据真实GPIO复用、HAL句柄、
  DMA/IRQ更新，并作为实际接线依据。

SVG/PNG和引脚表必须来自同一份连接定义；若两者冲突，以核对后的`.ioc`和实装
确认版引脚表为准，必须同步修图。

按以下顺序查找：

1. `docs/asset_index.md`：当前资产总入口；
2. `knowledge/`：硬件经验、测量边界、失败案例和算法条件；
3. 对应 Library 模块自己的 `README.md`；
4. `docs/verification/`：独立验证证据；
5. `docs/library/module_registry.md`：来源和生命周期；
6. 只有需要追溯时才进入 `projects/` 查看来源工程。

每个候选资产必须填写：

| 资产 | 能解决什么 | 当前等级 | 依赖 | 新题适配项 | 复验计划 |
|---|---|---|---|---|---|

选择规则：

- Knowledge 只提供经验和约束，不是可链接代码；
- `experimental / L2` 只证明主机软件行为；
- `L0` 模块只能作为接口草案；
- fake-bus 驱动不证明真实 SPI、GPIO、时序或模拟性能；
- 来源项目 L3/L4 不传递给提取模块；
- 板级参数、引脚、标定表和题目状态机不得跨题照搬。

## 8. 冻结选定方案与决策门

01.3 的三方案用于方向选择；本阶段只深入被用户选中的方案，并为其落实一个
可执行回退。比较：

- 是否覆盖全部验收项；
- 器件是否现有；
- 硬件和软件风险；
- 可在比赛时间内完成的验证闭环；
- 失败后能否降级完成基础要求。

在以下门通过前不得进入下一层：

| 决策门 | 通过条件 |
|---|---|
| G-1 三案决策 | 用户已选择 A/B/C、组合方案，或明确要求重做 |
| G0 需求冻结 | 验收矩阵覆盖全部题目条款 |
| G1 架构冻结 | 信号链、控制链、接口和回退方案明确 |
| G2 预算通过 | 采样、幅度、带宽、资源和误差预算可行 |
| G2.5 用户配置确认 | AI 已给出 CubeMX/接线/烧录清单；用户已完成配置并返回 `.ioc`、生成结果或实测证据 |
| G3 桌面验证 | 关键算法/协议有可重复的软件测试 |
| G4 板级最小链路 | 单器件、单通道、固定参数在实物通过 |
| G5 系统联调 | 自动状态机覆盖正常、超时、故障和恢复 |
| G6 题目验收 | 按题目条件逐项记录结果 |

具体生成、测量、特性识别和闭环架构的选择规则见 [`信号题方案架构手册.md`](信号题方案架构手册.md)。方案结论填写到 [`../templates/solution_architecture_template.md`](../templates/solution_architecture_template.md)，不得只保留在聊天中。

## 9. 建立新题工程

当前 `stm32f4-template/` 是本队 STM32F407 比赛板的默认新题起点，已有
Debug/Release 的 `L1 Builds` 证据。它还没有烧录、板级冒烟和 FPGA 通信证据；
复制后仍必须经过硬件用户门，不得把基线等级直接传给新题。

### 9.1 人机协作边界

CubeMX、接线、烧录和实物操作由用户完成。AI 在 G2 后只输出：

1. 外设、模式、时钟目标和引脚约束；
2. DMA/IRQ 需求、优先级关系和冲突检查；
3. 需要生成的工程选项；
4. 配置完成后的构建与最小冒烟测试；
5. 用户应返回的 `.ioc`、生成结果、日志和实测字段。

AI 给出清单后暂停板级阶段。只有用户明确说明配置完成，并提供当前工程证据后，
才能核对实际 HAL 句柄和生成代码，继续编写 Board Adapter 与应用集成。不得代替
用户操作 CubeMX，不得凭历史工程猜测配置，也不得把建议值写成已配置事实。

新工程应从受控的 CubeMX 基线建立，并保留：

```text
<project>/
├─ <project>.ioc
├─ Core/                  # CubeMX 生成层，仅在 USER CODE 区扩展
├─ Drivers/               # 对应当前 CubeMX/HAL 版本
├─ cmake/stm32cubemx/     # 生成构建清单
├─ User/
│  ├─ Inc/
│  └─ Src/                # 题目状态机、板级适配和应用服务
├─ CMakeLists.txt
├─ cmake/
├─ README.md
└─ docs/
   └─ verification/
```

建立工程时先复制根级 `stm32f4-template/`，再复制并填写
[`../templates/stm32f4_project_manifest_template.md`](../templates/stm32f4_project_manifest_template.md)。
当前准入状态见 [`../verification/stm32f4_template_gate.md`](../verification/stm32f4_template_gate.md)。
构建和烧录由用户按 [`STM32烧录指南.md`](STM32烧录指南.md) 操作；必须替换新工程
路径和 ELF 名称，并把日志与实测结果返回给 AI。

基线至少通过：

1. 空工程配置；
2. Arm 交叉编译；
3. 烧录；
4. LED/串口/系统时钟冒烟测试；
5. 一项 DMA 或定时器回调测试；
6. 记录 MCU、HAL、工具链和调试器版本。

## 10. Library 接入规则

接入模块时：

1. 阅读模块 README 和公开头文件；
2. 明确数据所有权、工作区大小、错误码和线程/中断语义；
3. 通过项目自己的 CMake 显式加入源文件或子目录；
4. HAL、GPIO、SPI、DMA 只在板级 adapter 中出现；
5. 先运行原主机测试，再增加项目集成测试；
6. 在 STM32 上记录 Flash、RAM、栈和最坏执行时间；
7. 板上回归后才能把新题使用记录标为 L3。

禁止直接复制整个旧项目的 `User/`、`Core/`、`Drivers/` 或固定 `app_config.h`。

## 11. 编码顺序

默认顺序：

1. 纯数学和协议内核；
2. fake bus / 主机测试；
3. 单器件板级 adapter；
4. 非阻塞服务；
5. 题目状态机；
6. UI 和日志；
7. 自动校准与故障恢复；
8. 完整验收。

驱动和服务优先采用：

```text
Init → Start → Service → IsDone → GetResult → Abort
```

ISR 只做最小搬运、时间戳或置位，不执行 FFT、浮点闭环、打印或阻塞通信。

### 11.1 首版代码结构质量门

比赛首版代码不是从空白架构自由发挥。结构设计应定向参考以下已完成题目的实战
形状，但不复制题目内容：

| 参考工程 | 只沿用的结构经验 | 不沿用 |
|---|---|---|
| `stm32f4-template/` | 唯一板级起点：当前 CubeMX/CMake 与板级外设配置 | canonical 目录上的直接开发、未经本题复验的硬件结论 |
| `projects/已完成项目/2025G/2025G` | 历史结构参考：集中配置、BASIC/ADVANCED模式、主循环推进多个Service | 题目参数、标定表、具体状态、历史回调和旧 `app.ioc` |
| `projects/已完成项目/test0` | 官方HAL启动顺序、MX初始化、定时器/DMA启动和构建闭环 | 巨型`main.c`、题目全局变量和调试残留 |
| `projects/已完成项目/FPGA_STM32高速采样桥` | 同型号板卡下的 FPGA 位流、SPI3 DMA、DRDY/ACK、接线和分层实现参考 | 把 25 MSPS 当连续上传速率、直接照搬引脚/时钟/窗口、继承来源 L3 |
| `projects/AI生成项目/2023D` | `capture/classify/estimate/hmi/selftest`职责拆分，`Init/Start/Service/IsDone`非阻塞接口 | 分类阈值、采样参数和当前dirty板级配置 |
| `projects/AI生成项目/2024C` | App上下文、`App_Init/App_Process`主循环、双通道/HMI/补偿模块边界 | 当前dirty实现、题目参数和未经新题复验的硬件结论 |

正式生成首版前必须满足：

1. `Core/`、启动文件、链接脚本和HAL来自本题CubeMX生成结果；
2. `main.c`只保留HAL/MX初始化、`App_Init()`和循环内`App_Process()`；
3. 题目参数集中在`app_config.h`并使用物理单位；
4. Adapter、Service、App职责分开，基础与发挥模式可独立启停；
5. HAL全局回调只有一个所有者或统一分发点；
6. 所有等待都有超时，所有输出链有可重复调用的Safe Stop；
7. CMake显式包含全部题目源文件，禁止依赖旧build产物；
8. 首版先完成编译、烧录、启动、GPIO/串口和单器件冒烟，再接整题算法；
9. BASIC链路未通过前，不让ADVANCED逻辑接管外设或回调；
10. 每个“已完成”结论都附构建、烧录或实测证据。

历史工程只作为结构证据。每次比赛仍须重新核对其当前路径、dirty状态以及本题
CubeMX/HAL事实，不自动继承来源工程的L3/L4。

“参考历史工程”不表示拼接多套源码。新题只有一个板级源头：根级
`stm32f4-template/` 的副本；2025G、test0、2023D和2024C仅在当前题目需要对应
能力时提供结构证据。某项结构在
多个工程中重复出现时，优先采用边界最清晰、最接近当前CubeMX/HAL且最容易验证
的一种，不重复实现。

“BASIC链路未通过前，不让ADVANCED逻辑接管外设或回调”具体表示：

- ADVANCED代码可以编译存在，但保持未启动状态；
- 不得由ADVANCED改写BASIC正在使用的TIM、ADC、DAC、SPI、DMA配置；
- 不得抢占或覆盖BASIC的DMA缓冲、HAL全局回调和中断状态；
- 不得在启动时自动切换器件模式、停止基础输出或修改基础标定；
- BASIC通过并冻结外设所有权后，ADVANCED只能经统一Adapter/回调分发点申请使用；
- ADVANCED失败或超时时必须释放外设并回到已验证的BASIC状态。

## 12. 每次结论的证据等级

| 等级 | 允许的结论 |
|---|---|
| L0 Draft | 接口或实现草案存在 |
| L1 Builds | 指定工具链下可构建 |
| L2 Software Tested | 独立软件测试通过 |
| L3 Hardware Tested | 指定板卡、接线和条件下实测通过 |
| L4 Contest Verified | 按正式题目条件完成验收 |

每次报告必须同时写明“验证对象、条件、结果、未覆盖项”。不得用“应该可以”“来源项目通过”替代当前证据。
