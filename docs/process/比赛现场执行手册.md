# 电赛信号题比赛现场执行手册

> 采样路线门：题目要求高速原始波形且 STM32 预算不足时，优先查看
> `K-FPGA-001` 和已完成项目 `FPGA_STM32高速采样桥`。先跑固定测试包，再接 ADC；
> 更换位流、引脚、ADC 时钟或主控 Adapter 后，原 L3 结论失效并需重测。

> 目的：把 Framework 的文档和资产变成比赛现场可执行动作。  
> 适用：拿到陌生信号题后，从读题到方案、CubeMX、编码、联调和交付。  
> 原则：先保基础分和可回退链路，再做发挥；框架整理不得阻塞比赛。

## 1. 唯一入口

现场不要遍历整个仓库。按固定顺序：

1. 读题目、勘误和器件限制；
2. 执行 [`新题启动SOP.md`](新题启动SOP.md)；
3. 用 [`../capability_matrix.md`](../capability_matrix.md) 标注能力码；
4. 从 [`../../knowledge/INDEX.md`](../../knowledge/INDEX.md) 取 Knowledge ID；
5. 从 [`../asset_index.md`](../asset_index.md) 选择 Library/脚手架/参考 App；
6. 填写 [`../templates/solution_architecture_template.md`](../templates/solution_architecture_template.md)；
7. 通过用户硬件门后再写 Board Adapter 和题目代码。

只有需要追溯来源、确认旧实现细节或寻找未提取能力时才进入 `projects/`。不得在
比赛开局扫描全部历史工程或直接复制旧项目。

## 2. 开局前三阶段：先让用户选择方向

比赛开局不得一次性展开完整方案、CubeMX 和代码。固定分为：

以下三个内部步骤全部属于 `01-新题方案与工程基线` 对话。

### 00. ChatGPT 器件级方案草案

为节省现场时间和 Codex 上下文，允许先把题目、器件清单、关键原理图/接口表和现场仪器条件发给 ChatGPT，让它只输出“用哪些器件、总体思路、连接图、是否需要 FPGA”的方案草案。固定提示词见 [`../templates/chatgpt_phase1_prompt.md`](../templates/chatgpt_phase1_prompt.md)。

此阶段不要求 ChatGPT 读取完整 Knowledge、Library、`.ioc`、FPGA 源码或历史工程；如果确实需要历史经验，由 Codex 读题后摘取相关内容再发给 ChatGPT。ChatGPT 草案不得作为工程事实，只能作为 `SOLUTION_USER_GATE` 前的候选输入。

FPGA 在本流程中是可选器件，不是默认架构。只有当 STM32、现有 ADC/DAC 或模拟器件无法满足采样率、同步性、时序稳定性或处理压力，并且 FPGA 的收益明显大于接线、位流、协议和调试复杂度时，才把 FPGA 放入主方案。

### 01.1 题目与资源快照

用户只需发送题目原文或清晰图片。AI 自动读取当前 `knowledge/器件知识库/器件清单.md`、
Framework 规则和流程，不要求用户重复发送器件清单。AI 只确认题目原文、基础/
发挥要求、禁止条件、现有主控、器件和仪器；缺失内容标 `待确认`。

### 01.2 快速检索

只检索与题目直接相关的 Knowledge、Library 和器件清单，形成候选能力，不扫描
全部历史工程，不开始写代码。

### 01.3 三方案决策门

AI 首次方案输出严格限制为三种：

1. **A 现有器件优先方案**：依赖现场已有器件，也允许用现有芯片、阻容和通用
   器件自行焊接电路，目标是最快形成基础闭环；
2. **B 性能增强方案**：允许加入当前没有、需要额外采购的必须器件，或能显著
   改善精度、带宽、稳定性和调试难度的关键芯片/成品模块；
3. **C 保底/不同架构方案**：强调低风险、可回退，或采用与 A/B 不同的测量/生成
   路线。

每种方案此时只写：

- 核心信号链和要完成的基础/发挥要求；
- 所需器件，并明确“已有 / 库中可查 / 必须新增 / 待确认”；
- 主要优点、主要缺点；
- 最大技术风险和预计调试工作量；
- 能否在现有时间内形成基础闭环；
- 推荐顺序。

方案包含自焊电路时，还必须列出关键 BOM、预计焊接/调试时间、关键测点和
失败后的旁路/替代方案。元件在器件清单中只证明“可考虑实现”，不证明电路已经
焊好或通过板级验证；高速 PCB、阻抗控制、热稳定或复杂标定风险过高的自焊电路，
应转入 B/C 方案或降级为备选。

随后进入 `SOLUTION_USER_GATE`，AI 必须暂停，等待用户选择 A/B/C、要求组合方案
或否决重做。在用户决策前，不生成完整方案文档，不给 CubeMX 操作清单，不创建
题目工程，不编写正式代码。

用户选定后，仍在 `01-新题方案与工程基线` 对话中进入“完整方案与工程基线”，
补齐以下内容。

完整方案冻结后、进入CubeMX前，AI还必须交付：

- 硬件连接示意图建议版：可编辑SVG及同内容PNG；
- 按模块分组的STM32程控/信号引脚总览。

用户回传`.ioc`后，两者必须更新为实装确认版。仅供电连接不逐项进入引脚表，
但所有模块仍必须按要求供电并共地。详细格式见
[`新题启动SOP.md#71-方案确认后的硬件交付物`](新题启动SOP.md#71-方案确认后的硬件交付物)。

### 输入

- 题目原文、勘误、基础/发挥分值；
- 现有主控、模块、器件、仪器和队员分工；
- 题目总时间和禁止条件。

### 用户选定后 AI 必须输出

1. 验收矩阵；
2. 信号链和控制链；
3. 频率/采样、幅度、带宽/建立时间、资源/实时性、误差五类预算；
4. 被选方案的完整架构、保底分支和明确回退条件；
5. Knowledge/Library 调用表；
6. 未知项、否决条件和最晚回退时刻；
7. CubeMX 配置清单草案。

此阶段不写固定引脚、HAL 句柄或猜测的 DMA 映射。

## 2.1 多对话任务分配

比赛项目不要求塞进一个超长对话。默认使用：

| 对话 | 职责 | 允许修改 | 完成后交接 |
|---|---|---|---|
| 01-新题方案与工程基线 | 自动读取器件/资产、三方案、用户决策、完整方案、2025G `.ioc` 副本、CubeMX 核对、最小构建和烧录 | 状态/方案文档及 Core/Drivers/构建配置的受控范围 | 方案选择、`.ioc`、句柄、构建/烧录日志 |
| 02-基础功能 | 单器件、单通道、固定参数、BASIC 状态机 | Adapter/Service/App 基础部分 | 基础验收和最后可恢复 commit |
| 03-发挥功能 | 自动化、识别、闭环、标定等发挥项 | 已冻结接口上的增量文件 | 发挥项证据、失败时回退方法 |
| 04-联调验收 | 整机回归、故障、超时、操作说明和冻结 | 验证记录与必要的最小修复 | 最终固件身份和验收矩阵 |

`01-新题方案与工程基线` 建立项目的权威状态和方案文件。每个后续工作对话开始前
必须读取项目内的 `docs/project_status.md`、方案文档、目标仓库 `git status` 和
上一阶段日志；结束前更新状态文档。聊天记录不是唯一交接载体。

### 选定方案后的二次资产核对

用户通过 `SOLUTION_USER_GATE` 后、正式编写代码前，AI 必须按选定方案再次定向
读取：

1. 相关 Knowledge 正文、适用条件、失败案例和复验要求；
2. 相关 Library 模块 README、公开头文件、依赖和验证记录；
3. 当前器件清单以及器件数据手册或本地资料中会影响设计的参数；
4. 根级 `stm32f4-template/` 板级基线、本题实际 `.ioc`，以及选定 FPGA 路线时
   `projects/已完成项目/FPGA_STM32高速采样桥/` 中直接相关的位流、接线和 Adapter 证据。

只有这次核对完成，才能决定复用、改写或放弃哪些资产。不得仅凭开局快速检索、
文件名或历史项目成功就开始复制代码。

首版代码结构还必须执行
[`新题启动SOP.md#111-首版代码结构质量门`](新题启动SOP.md#111-首版代码结构质量门)：
参考2025G、test0、2023D和2024C的实战工程形状，重新生成本题内容，不复制历史
题目参数和整套源码。

同一时刻只允许一个对话拥有同一组文件的写权限。基础和发挥可以分对话，但发挥
对话不得在基础分支未冻结时改写基础链路；确需并行时使用不同分支/独立 worktree，
并由用户明确批准合并。

## 3. 方案优先级

按以下顺序保交付：

1. 能稳定完成基础要求的单链路方案；
2. 能观测错误和超时的自动状态机；
3. 可标定、可重复的测量；
4. 发挥功能；
5. 代码通用化和赛后 Library 提取。

同一功能有多种实现时，优先选择：

- 已有器件和接线；
- 测量能力满足 Nyquist、量程和带宽；
- 可在现场快速验证；
- 失败后可以切换到固定参数、低频、单通道或 BASIC 模式；
- Adapter 边界清晰，不要求重写 CubeMX 生成层。

## 4. `HARDWARE_USER_GATE`

AI 给出逐项清单后暂停，用户完成：

- CubeMX 的 MCU、时钟、引脚、外设、DMA、NVIC 和代码生成；
- 接线、供电、端接、探头和仪器设置；
- 首次空工程构建；
- 必要的烧录与最小实物冒烟。

用户至少返回：

```text
工程绝对路径：
.ioc 路径：
MCU/板卡：
生成是否成功：
构建是否成功：
实际 HAL 句柄：
实际 DMA/IRQ：
接线与供电：
最小冒烟结果：
日志或错误全文：
```

没有这些事实，AI 只写纯算法、协议、接口和 fake，不写猜测的板级代码。

## 5. 代码落地顺序

通过硬件门后，AI 按以下顺序工作：

1. 冻结 [`../templates/board_adapter_contract_template.md`](../templates/board_adapter_contract_template.md)；
2. 建立题目配置和物理单位；
3. 接入纯 DSP/协议模块；
4. 实现单器件 Adapter；
5. 实现非阻塞 Service；
6. 实现 BASIC 状态机；
7. 完成单通道/固定参数最小链路；
8. 增加 ADVANCED、闭环、自动标定或识别；
9. 增加 UI、日志、错误码和 Safe Stop；
10. 填写 [`../templates/code_delivery_checklist.md`](../templates/code_delivery_checklist.md)。

CubeMX 生成文件只在 USER CODE 保护段修改。题目逻辑优先放 `User/Inc` 和
`User/Src`，不把题目状态机塞进 Library。

## 6. 每轮联调循环

每次只改变一个主要变量：

```text
现象 → 当前证据 → 最可能层级 → 最小修改 → 用户构建/烧录 → 实测 → 结论
```

排查顺序：

1. 供电、地、接线、端接、探头；
2. CubeMX 和真实句柄；
3. 时钟、DMA、IRQ、回调所有权；
4. 单器件通信；
5. 原始数据和量程；
6. DSP/判决；
7. 自动流程和 UI。

串口读数必须与示波器或已知输入互相校验。没有原始量和实测条件时，不直接调
分类阈值、补偿表或闭环参数。

### RST 前后串口抓取

需要观察刚按 RST 后的启动、FPGA 握手或 ADC 数据时，不使用“先按复位、再打开
串口”的顺序。固定流程为：

1. USB 转串口接好，关闭所有串口助手，避免 COM 口被占用；
2. 在 Signal 根目录启动
   [`../../tests/tools/serial_rst_capture.ps1`](../reproduction.md)；
3. 看到 `CAPTURE_READY` 后，用户再按指定的 STM32 或 FPGA RST；
4. 保持硬件不动，等待本轮指定的抓取时间结束；启动瞬间通常取 10～15 秒，
   偶发问题可取 60～300 秒，不固定时长；
5. AI 读取原始日志和摘要，先判断启动、心跳、FPGA/ADC 数据、CRC/帧头错误及
   序号变化，再决定是否修改代码。

当前 STM32F407 比赛板调试口默认参数为 `COM5, 115200, 8N1`；COM 号变化时通过
`-Port` 参数指定，抓取时间由 AI 按本轮调试目标通过 `-DurationSeconds` 指定。工具用法、退出码和日志位置见
[`../../tests/tools/README.md`](../reproduction.md)。脚本只监听和保存，
不会代替用户按 RST、烧录或操作硬件。

## 7. 失败与回退

触发以下任一条件立即评估回退：

- 关键测量超过 Nyquist、量程或器件带宽；
- 单器件在预定时间内仍不稳定；
- 自动流程无法观测故障或无法安全停止；
- 发挥功能开始破坏已通过的基础链路；
- 剩余时间不足以完成一次完整复验。

默认回退梯：

```text
ADVANCED 自动闭环
→ BASIC 固定参数
→ 稀疏频点/单通道
→ 降低频段或改用 RMS/检波
→ 保留基础要求并冻结
```

回退必须通过明确代码模式、配置或跳线实现，不能依赖临场改源码。

## 8. 现场验证最小集

### 每小时版本检查点

比赛开始后，以项目启动时间为基准，每满 60 分钟触发一次询问：

```text
已到版本检查点。是否要提交当前可恢复版本？
```

- 只提醒，不自动执行 `git add` 或 `git commit`；
- 用户选择“是”后，先显示目标仓库、分支、`git status`、拟提交的精确文件和
  验证状态，再等待用户确认提交范围；
- 用户选择“否”时，在 `docs/project_status.md` 记录跳过时间和原因，继续工作；
- 若当前正在烧录或硬件测量，在该原子步骤完成后立即补问；
- Codex 对话关闭或没有任务运行时不能自行后台发消息。需要独立准点提醒时，启动
  [`../../tests/tools/contest_commit_reminder.ps1`](../reproduction.md)；
  该脚本也只询问，不执行 Git。

### 每次构建后

- 构建目标和退出码；
- 重要警告；
- ELF/MAP、Flash/RAM；
- 本轮实际修改文件。

### 每次烧录后

- 固件身份或时间戳；
- 启动日志；
- Safe Stop；
- 单器件/单通道冒烟；
- 与上一个可用版本的差异。

### 冻结基础功能前

- 基础要求逐项至少一次完整流程；
- 断电重启；
- 重复按键；
- 超时/断线/饱和；
- 回退模式；
- 最终接线和仪器条件。

烧录步骤按 [`STM32烧录指南.md`](STM32烧录指南.md)，由用户操作。

## 9. 交付冻结

冻结版本时保存：

- 题目、勘误和验收矩阵；
- 方案架构和资产调用表；
- `.ioc`、生成代码、User 代码和构建配置；
- Board Adapter 契约；
- 标定数据及适用条件；
- 构建、烧录和实测记录；
- 操作说明、已知问题、回退方式；
- Git 分支、commit/dirty 边界和最终固件身份。

未经用户确认的实测项保持 `待验证`，不得因为比赛时间结束自动写成 L4。

## 10. 赛后沉淀

赛后按顺序：

1. 先冻结题目工程和证据；
2. 更新项目复盘；
3. 把硬件方法、限制和失败案例写入 Knowledge；
4. 为新 Knowledge 分配稳定 ID；
5. 评估纯算法、协议或 Service 是否值得进入 `library/experimental`；
6. 新提取模块从自身证据重新评级；
7. 更新能力矩阵和资产索引。

比赛期间的临时参数、固定引脚和整题状态机不直接进入 Library。
